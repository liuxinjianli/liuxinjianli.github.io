模块 0 ｜ 作品集核心逻辑THE LOOP

三个项目不是孤立的练习，而是按真实店铺运营的先后顺序咬合的一条链：

  • 售前（项目一）先把商品“卖出去的前提”做好：用 AI 工作流按 Amazon US 规范产出 Listing，让关键词布局、字符合规、英文表达在上架前就一次到位；
  • 售中（项目二）再把“卖的过程”盯住：每日销售、广告、库存数据进一张 Excel 看板，公式自动算 ACOS、盈亏线、可售天数，异常当天就以风险标签的形式跳出来；
  • 售后（项目三）最后把“卖完之后的反馈”用起来：竞品差评先归因，再沉淀为分级客服话术，而归因结论不止于处理客诉，还要反哺回售前和售中——差评里暴露的主图没讲清、说明书看不懂，反过来改主图和说明书；风险标签里频繁出现的断货、广告超标，反过来调整库存与广告策略。闭环转起来，同一批问题就不会重复发生。

模块 2 ｜ 售中 · 多平台运营与库存预警轻量化看板IN-SALE

结构：Daily_Log（按日流水）+ Config_Params（参数表）。所有阈值集中在参数表、公式绝对引用，公式内不写死任何阈值；所有除法用 IFERROR 包裹。当前参数：ACOS 预警阈值 30%、断货预警 14 天、积压预警 90 天、自然流量占比阈值 30%、安全边际 5%。

2.2 核心计算公式（与工作簿逐字一致，以第 2 行为例）

M2 · ACOS（有花费无出单时单独标注，绝不显示为 0%）
=IFERROR(IF(OR(F2="",G2=""),"数据缺失",IF(AND(F2>0,G2=0),"异常：有花费无出单",F2/G2)),"数据缺失")

P2 · 盈亏平衡ACOS（动态预警线 = 毛利率 − 安全边际，随每个 SKU 的毛利率浮动）
=IFERROR(IF(O2="数据缺失","数据缺失",O2-Config_Params!$B$6),"数据缺失")
（其中 O2 毛利率 = (E2-J2-K2)/E2，成本项任一缺录即标"数据缺失"）

R2 · 可售天数 DOH（日均销量为 0 时标"无销售数据"，不输出虚假的大天数）
=IFERROR(IF(OR(H2="",I2=""),"数据缺失",IF(I2=0,"无销售数据",H2/I2)),"数据缺失")

S2 · 复合风险标签（TEXTJOIN 拼接多标签；每个数值比较前先用 ISNUMBER 守卫）
=TEXTJOIN("、",TRUE,
   IF(AND(ISNUMBER(M2),ISNUMBER(P2),M2>P2),"广告超标",""),
   IF(AND(ISNUMBER(M2),ISNUMBER(P2),M2<=P2,M2>Config_Params!$B$2),"广告预警",""),
   IF(ISNUMBER(SEARCH("有花费无出单",M2&"")),"有花费无出单",""),
   IF(AND(ISNUMBER(R2),R2<=Config_Params!$B$3),"断货风险",""),
   IF(AND(ISNUMBER(R2),R2>=Config_Params!$B$4),"积压风险",""),
   IF(AND(ISNUMBER(Q2),Q2<Config_Params!$B$5),"自然流量不足",""),
   IF(R2="无销售数据","无销售数据",""),
   IF(OR(M2="数据缺失",…),"数据缺失",""))   —— 全部为空时显示"正常"

设计要点：双线并行——“广告超标”看动态盈亏线（这个品实际亏不亏），“广告预警”看固定阈值线（还没亏、但已越过统一警戒线），先预警、后超标；一个 SKU 可同时挂多个标签，不用嵌套 IF 互相掩盖风险。

2.5 价值小结

  • 数据敏感度：不只看销售额，用毛利率推导出每个 SKU 自己的广告盈亏线，低毛利品不会被“统一阈值”误伤或漏报；
  • 风险前置：断货按可售天数提前 14 天报警，广告异常当天出标签，把事后复盘变成事前处置；
  • 后续自动化升级路径（方案建议，本阶段未实现）：数据导入可走 Power Query / 平台 API / 第三方 ERP 三条路径递进，预警推送可用 VBA + 企业微信/飞书 Webhook 或 Power Automate——均为方案层建议，当前交付的是公式预警静态版。

模块 3 ｜ 售后 · 竞品差评溯源分析与客服 SOPAFTER-SALE

对象产品：车载磁吸手机支架。工作顺序：差评归因 → 交叉假设 → 分级话术 → 合规红线 → 反哺选品，归因结论先过数据校验再投入动作。

样本口径：竞品 1–3 星差评 100 条归因统计；样本 ASIN 清单与统计时间区间尚待补齐，补齐前本节排序与 3.3 的优先级均按“暂定”执行；另需确认噪音评论清洗、改款前后切分与星级分层（100 条样本占比误差可达约 ±10 个百分点，涉及高成本动作前须扩样复核）。

交叉归因（示例）：说明书不清 → 买家装错/用力过猛 → 断裂后被评论为“材质差”，即材质类差评中可能混有说明书根因——所以反哺顺序是先改说明书、再评估供应链升级，避免把说明书问题误判成供应链问题。

  • 禁止用任何金钱、折扣、礼品直接交换评价修改或删除——在亚马逊规则下，索取、诱导或施压买家改/删评价属高压线违规；一切补偿只作为服务补救出现，绝不与评价同函；
  • 首选路径只有两条：站内沟通只解决问题、全程不提评价；需要邀评时只用官方 “Request a Review” 按钮。本知识库另备一个“问题已解决且买家主动表示满意后、限用一次”的中性邀请模板，明确定位为灰区谨慎使用、不回应永不追问。

3.5 价值小结

  • 客服不止于回复：先归因、再分级，同类问题用最低够用的成本层级解决，兜底层级明确封顶、不无限谈判；
  • 用差评反哺产品：三项改进各有责任方与复盘周期，客服数据直接变成选品和 Listing 的改进输入——这正是模块 0 闭环的回流段；
  • 合规先行：评价红线写进 SOP 本身，情绪升级另有高危关键词清单与 SLA（高危触发 ≤1 小时人工接管），避免为短期指标伤账户。
